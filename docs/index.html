    Application architecture

    How ServiceTracer works

    The page above shows the incident result. This map explains the request path, the private application security boundary, and how correlated backend evidence becomes a bounded diagnostic report.

    Current collector-hosted golden path
    Zone 1 Public presentation and ingress
    Browser GitHub Pages frontend Loads the operator console, checks /api/health, and sends POST /api/demo/run.
    Name and address Azure DNS → pip-st-demo-api-mst-dev Resolves the public ServiceTracer hostname to the dedicated Standard public IP.
    Controlled ingress lb-st-demo-api-mst-dev Forwards TCP 80/443 to the private collector. The load balancer does not inspect the application request or terminate TLS.
    TCP 80/443
    Zone 2 Private application security boundary
    Mediated access only
    Private collector vm-stcollector-mst-dev · 10.20.40.10 The collector has no directly attached public IP. NSG rules admit only the required web path from the public ingress.
    Security gateway Nginx reverse proxy Terminates TLS, redirects HTTP, rate-limits analysis requests, restricts request size, and exposes only the approved API routes.
    Application process Python API · 127.0.0.1:8090 Listens only on loopback, validates the browser origin, creates request identities, and runs bounded parallel transactions.
    HTTPS /transaction
    Zone 3 Synthetic remote-access service
    Traffic distribution lb-remote-access-mst-dev Distributes each correlated transaction across the two synthetic VPN backends.
    Backend vm-vpn01-mst-dev Returns a successful synthetic transaction.
    Backend vm-vpn02-mst-dev Returns a controlled dependency failure for localization.
    Evidence output Correlated comparison ServiceTracer compares backend outcomes, preserves uncertainty, and reports where a technician should continue investigating.
    ↩ Return path: structured backend evidence travels back through the collector API and demo API load balancer, then the browser renders the finding and investigation boundary.

    Request walkthrough

    1. The browser verifies the live API health contract and Azure host identity.
    2. The operator starts a bounded incident-analysis request.
    3. The dedicated public load balancer forwards TCP 443 to the private collector.
    4. Nginx applies the public security controls and proxies the accepted request to loopback.
    5. The Python API creates unique correlations and sends bounded parallel transactions.
    6. The remote-access load balancer selects VPN-01 or VPN-02 for each transaction.
    7. ServiceTracer compares successful and failed outcomes without inventing an exact root cause.
    8. The frontend renders the finding, evidence summary, and technician-owned next steps.

    Evidence and truth boundaries

    load_balancer_probe_healthy != complete_transaction_healthy
    resource_deployed != service_validated
    API_reachable != backend_dependency_healthy
    finding_localized != exact_root_cause_proven

    The live provenance panel remains the authority for the currently observed endpoint, Azure identity, deployed source, request correlation, and transaction state. This architecture section explains the path; it does not manufacture runtime proof.
